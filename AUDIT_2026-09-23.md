## Audit 2 — Architecture & fiabilité multi-bots (8.75)

### 2.1 Points forts vérifiés (CONFIRMED)

- **Cycle update sain** : `cmd_update` = verrou (flock + stale 15 min) + `trap … EXIT` + arrêt du bot PENDANT install/build (contention mémoire 8.29) + `update_fail` qui relance l'ancien build + restart final. Avec 8.75 : `cmd_stop` balaie aussi les moteurs enfants (`engine_pids`, pattern `dist/engine[.]cjs` distinct du pattern panneau → `is_running`/watchdog ne confondent pas).
- **Orphelins impossibles** : chaque moteur compare `process.ppid` toutes les 5 s et s'arrête si le panneau disparaît ; le watchdog ne relance que le panneau, qui relance les moteurs.
- **Crash isolé** : exit imprévu → backoff exponentiel 5→10→20→40→60 s (plafond), compteur remis à zéro après 10 min de stabilité ; timers `unref` (ne bloquent pas l'exit). Prouvé en E2E sandbox (SIGKILL d'un moteur → relance en 5 s, l'autre bot jamais impacté).
- **Arrêt gracieux** : SIGTERM panneau → `stopAll()` (stopLiveBot par moteur, force-exit 15 s) ; SIGTERM moteur → fermeture session + exit 0 (prouvé E2E : « moteur arrêté (code 0) »).
- **Démarrage échelonné** 1,5 s entre moteurs (pic CPU/RAM évité sur petit VPS).
- **Isolation stricte** : un dossier auth + un dossier data par bot, envoyés par env (`NEBULA_AUTH_DIR`/`NEBULA_DATA_DIR` préexistants), persona par bot (`NEBULA_AI_PERSONALITY` préexistant).
- **Compat zéro-migration** : sans bots.json → bot unique « nebula » sur les chemins historiques ; E2E vérifié (dossiers legacy utilisés, bot2 isolé sous bots/bot2/).
- **Contrat proxy stable** : le panneau ne transmet pas le cookie de session (Bearer seul), transmet host/x-forwarded-* pour que les enfants calculent les mêmes URLs publiques.

### 2.2 Constats

```text
Severity: MEDIUM
Confidence: CONFIRMED (par lecture de code ; non reproduit en test)
Category: Fiabilité / fuite de ressources
Location: src/bot/botSupervisor.ts:455 (proxyRequest) et :505 (proxyMediaProbe)

Problem:
`upstream.data.pipe(res)` sans gestion de la fermeture prématurée de la
réponse client. Si le client coupe (navigation, annulation, perte réseau)
pendant un gros téléchargement média, le flux amont continue d'être téléchargé
jusqu'à completion : socket + bande passante consommés pour personne.

Evidence: aucun handler `res.on("close")` / `req.on("aborted")` dans les deux
fonctions ; pipe direct.

Impact: gaspillage de ressources locale (et amont) sur les gros médias
(zips de batch jusqu'à 2048 Mo) ; accumulation possible de sockets en
ATTENTE_CLOSE si des clients coupent en rafale.

Root Cause: le pipe axios→express ne propage pas l'annulation automatiquement.

Recommended Fix:
  res.on("close", () => { if (!res.writableEnded) upstream.data.destroy(); });
dans les deux fonctions. + test d'intégration (client abort).

Regression Risk: faible — comportement inchangé quand le client consomme tout.
```

Déjà documenté dans MULTI_BOTS.md ; garde-fou disque global inter-bots toujours absent (plannifié session 3).
